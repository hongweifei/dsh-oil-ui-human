# 视觉评审派发协议（主代理专用）

主代理使用本文件派发独立评审。打分标准与检查规则记载于 [评审手册](reviewer-manual.md)，由评审者阅读；主代理无需阅读该手册，只按下列清单执行交接。

## 1. 派发时机与模式选择

完成一个关键页面、设计方案或改动之后，按下表触发对应的评审子代理：

| 改动类型 | 子代理的提示词（Prompt）模板 |
| --- | --- |
| 探索了新界面，或推翻现状重新设计（重塑） | `按照你系统提示词中已内置的《视觉与交互评审手册》【全新界面与改版评审】标准，评审这些截图，并给出 1-10 的打分。` |
| **为已有界面评审**：在已有界面上整理、升级、润色或扩展 | `按照你系统提示词中已内置的《视觉与交互评审手册》【存量已有界面润色评审】标准，对比提供的现状规范，指出偏离点。不打分。` |
| 小改动、单处间距或颜色微调 | **无需派发子代理**，主代理结合上下文自行核对即可。 |

子代理启动时已由插件自动将《视觉与交互评审手册》（`references/reviewer-manual.md`）注入其系统提示词，主 Agent 只需调用 `subagent` 传入下方交接清单与对应模式指令，无需附带手册路径，也无需让子代理再次读取手册。

## 2. 派发前主代理须准备的交接清单

调用宿主提供的隔离执行能力时，必须提供以下材料：

- **必须提供**：当前版本的截图或录屏（须注明设备视口）、用户的原始任务、设计边界与约束条件；有方向卡时，另行提供北极星那一句。方向卡中其他需要评审者知悉的硬性约束（例如品牌要求每屏出现字标），应摘录为一句写入约束，不提交整张方向卡。
- **如具备则提供**：现有项目的色彩规范、组件约束（存量老项目必须提供）；方向卡的选色记录，即其中说明"该颜色来自这个产品的什么"那一句；项目内存在 `DESIGN.md` 或同类设计文档时，存量润色评审整份给出并以它作为标准，新界面与改版评审只将其中品牌资产和"不要做"事项摘入约束。
- **截图工具的可读性提示**：将 `report.json` 中 `lint` 字段的提示原样给出；这几项影响实际阅读，应予修正，误报写一句说明即可。
- **不得提供**：源代码、为自身做法辩护的说明、此前评审打过的分数（评分须保持独立）。

截图必须属于当前版本，且能被评审者访问；本轮未改动的状态和动效，可以沿用上一轮的证据文件，交接时注明哪些属于沿用。长页面须同时提供整页图与必要的局部图；局部细节图不能替代整体构图。

动效无需逐项准备证据：将取证那一次的录屏一并交给评审即可。评审者能够自行打开页面时，把页面地址也提供给它，录屏中看不清的部分它会自行操作复核。

没有隔离且能看图的执行者时，主代理按同一手册自检，交付时写明"未独立评审"；没有实际画面时不给出视觉分数。

## 3. 主代理处理子代理反馈的原则

子代理返回报告后，按以下原则执行修改：

- **第一条为"重做"时**：回到方向卡，重新确定被点名区块的骨架或主视觉，不逐条修补。
- **按清单顺序修改**：问题清单自影响最大的一条起依次处理；"保留"那一行记入设计说明，修改时对照执行，不得将其磨平。
- **提升条目同样要落实**：精致度、设计感和动效的提升并非可选建议，与问题一样按清单执行；确实无法实现的，在交付说明中写明原因。
- **默认照删**：子代理列出的"可以直接删掉的无用文字"应当删除，除非删除会产生功能歧义。
- **落实为具体调整**：将子代理的高层要求（如"太挤"、"层级不清"）转化为间距、字号和阴影的实际调整。子代理提议更改用户已锁定的品牌色或大框架时，写明一句理由后不予采纳。
- **防止陷入死循环**：若双方审美意见陷入僵持、来回反复且没有可见收益，保留你认为最佳的版本并终止循环。
