# Oil UI Design Skill

## 设计原则

界面设计应以明确的设计定位为核心导向，确保构图、字体、色彩、素材和交互等视觉元素均围绕该定位展开，形成具有高度辨识度的统一界面风格。设计的克制并非将所有风格打磨成平庸的中性状态，而是通过保留最具表现力的设计选择、去除缺乏价值贡献的冗余元素来实现。界面美观度与功能可行性应作为两个独立的验收维度分别评估。

设计风格应从页面的业务品类、首屏核心内容与品牌形象中自然推导得出，而非依赖模型的通用模板。动手之前先想清楚几件事：该界面所属的业务品类；目标用户在首屏的核心诉求与期望完成的操作；同类优秀产品在首屏与控件上的做法。这几项是推导的起点，不是固定必答清单，可按任务裁剪。设计方案的创新点应建立在上述基础之上的合理偏离，且偏离理由必须与该产品的具体特性相关联。

## 方法体系

相关工作方法与评审协议均位于本目录之下；截图、素材、生图与对比页能力由插件工具 `oil_ui_shoot`、`oil_ui_media`、`oil_ui_image`、`oil_ui_explorer` 与 `oil_ui_skill_status` 提供，工具用法详见 [工具指南](references/tools.md)，无需为此单独加载其他 Skill，也不需要执行本目录内的脚本。先调用 `oil_ui_skill_status` 确认生图工具可用状态（`imageGenAvailable`）与 Skill 目录。前端实现方案应遵循项目既有的技术规范与约定，若宿主环境或项目规范明确要求加载特定 Skill，则按规范要求执行。相对路径引用均从本文件所在目录开始计算。
## 范围界定

### 需求分析

首先依据用户请求、现有页面状态与参考资料，明确以下要素：目标用户群体是谁、核心任务是什么、存在哪些真实内容载体、主要使用设备为何、最终交付物形式为何。分析过程应聚焦于相关信息区域，避免对整个项目进行无差别的全面浏览。

### 语言与文案

回复内容、设计说明文档及交付说明均应采用用户使用的语言；界面文案应采用产品面向最终用户的语言，若未作明确说明则跟随用户所使用的语言。本 Skill 以中文编写，不应因用户使用英文而混入不必要的中文内容。

### 约束优先级

用户已确定的品牌规范、参考素材、页面结构与交互约束应享有最高优先级。应准确区分用户需求属于风格借鉴、重新设计还是精准还原类型，不得擅自更换设计目标。

### 提问策略

仅在缺失的信息会直接影响核心设计方向且无法通过合理推断得出结论时，才进行一次性集中提问；对于可以自行决策的细节，应由设计者直接决定并说明假设依据。

### 交付物区分

设计说明、设计稿、原型系统与可运行的产品是四种不同的交付物形态。用户仅要求进行评审时不得修改文件；用户仅要求进行设计时，不应默认修改业务代码。

| 当前范围 | 处理规范 |
| --- | --- |
| **小范围修改**：用户明确指定了待修改的元素及具体修改方式，例如修改文案内容、调整间距数值、删除指定元素，或提出"将保存按钮改为绿色""增加此处间距"等明确要求 | 直接执行修改，交付时用一两句话简要说明；跳过前述的推导起点确认，不进行现状盘点、不开启新方向探索、不启动评审流程。仅涉及文案、数量、指定元素删除或复用现有样式的修改，在完成代码修改后即可交付，无需开启浏览器查看视觉效果；涉及颜色、间距或样式调整的，应在目标视口下查看改动位置及其相邻元素的显示效果。仅笼统表示"页面某处显得别扭"或"不够美观"希望优化，但未明确指出具体修改对象的，不属于小范围修改范畴 |
| **新界面设计或明确要求进行重新探索** | 按照阶段一至阶段五的流程执行：先提出若干存在实质差异的方案供用户选择。数量与形式按任务判断：能从文字描述中定下来的，就不必都做成页面；希望看到实际效果的，再把候选做成首屏放入对比页。方案数量与呈现深度由内容决定，不设固定配额。用户选定后只针对所选方案继续推进。关于不适用的特殊情况，参见阶段一中的补充说明。仅要求交付设计说明时，工作止于方向决策的记录，并说明尚未进行可视化渲染 |
| **用户已选定设计方案，或本次任务需继续深化已确认的方向** | 保留已选定的方向，直接从阶段二进入后续流程，仅检查受影响的区域与状态 |
| **单个组件设计，追求极致打磨或建立辨识度** | 按照阶段一至阶段五的流程执行，但工作范围仅限于该组件；仅针对单一方向进行设计：首先确立视觉主角，从中提取色彩体系，将主要精力集中于主操作时刻的视觉呈现 |
| **存量项目中优化用户界面、调整流程或新增功能** | 首先明确用户的具体需求类型：优化用户界面时可重新确立偶然形成的视觉默认值，但需保留品牌资产；调整流程与新增功能则应沿用既有视觉体系，不执行阶段一中的视觉方向探索流程。盘点现有页面结构、设计变量与共享组件，留存基准截图，从源头进行修改 |
| **截图还原** | 按照 [布局与视口规范](references/layout-and-viewport.md) 中的"精准还原"流程执行：以参考图为视觉基准，确定参考视口与布局约束后进入阶段二，不进行发散性的新风格探索；每轮修改完成后使用 `oil_ui_shoot` 的 `compare` 参数与参考图进行比对验证 |
| **用户界面与用户体验评审** | 按照阶段四委派评审人员，仅提供诊断意见而不实施修正；交付证据材料与设计建议 |

## 阶段一：方向探索与收敛

在设计方案尚未确定的情况下，本阶段仅阅读方向探索所需的参考资料，不提前查阅阶段二至阶段五的相关文件。工作流程参见 [设计方向指南](references/design-direction.md)：辨认业务品类、拆解标杆案例、确立设计调性、提出设计方向。在撰写文案之前应先确定首屏布局框架：结构由该页的内容与目的推导，不套用固定配方；每个方向均需记录方向决策并进行差异化检验。若需制作首屏对比页面，请另参阅 [风格对比页指南](references/style-explorer.md)。

### 文字提案先行

**提案先行。** 完成品类辨认与标杆拆解后，先以书面形式提出若干风格各异的方案，暂不制作页面。每个方案说清：整体视觉感受、首屏形态、字体与色彩体系、主视觉如何呈现，并附上推荐及理由，再征询用户：按其中一个直接推进，还是做成首屏并列比较。需要用户表态时才停下来等回复；信息已经足够、或用户已说明偏好，就直接继续做。

- 若用户选定某一方案，或从描述中已能明确其偏好：设计方向即告确定，仅需针对该方案继续推进，不制作对比页面。动手实施前应参照 [设计方向指南](references/design-direction.md) 中的"差异化检验"要求，将该方案与已拆解的标杆案例进行并列比对，确认不存在视觉雷同问题。
- 若用户希望看到实际视觉效果：按下一段的流程把候选方案做成首屏。
- 此后凡是需要提供多个候选方案供用户选择的场景，均应按此流程先用文字进行初步提案：若用户能够从文字描述中作出决策，则仅制作所选方案；若用户希望看到实际视觉效果再行制作。

### 三方案并行制作

**用户要求查看实际画面时，把候选方案做成首屏。** 每个方向都是真实的首屏内容，在布局框架、字体体系、色彩方案与主视觉呈现上相互区分，并列放入对比页面供用户选择。数量按实际需要决定，不做凑数。仅制作能够体现风格特征的必要元素：

- 每个方向为一个独立的 HTML 文件、一个固定视口尺寸、仅展示首屏部分（不向下延伸至完整页面）、仅呈现主交互状态；不包含交互细节说明、不支持响应式布局与动画效果、不进行取证测试、不委派评审人员。若宿主环境支持并行写入文件或启动子 Agent，各方向可并行编写。
- 各方向共用同一份示例文本与数据，仅编写一次。结构与样式应各自独立编写：不使用同一模板通过替换多组样式的方式生成，以免几个方向的布局框架本质上完全相同。
- 依赖图像作为主视觉的方案，每个方案生成一张图片，不满意时可再重新生成；其余图像占位符使用从页面提取的色彩色块进行替代。
- 对候选目录执行一次截图操作（单次操作即可输出各方向的缩略图与并排总览图 `sheet.png`）进行自查，修正重叠、裁切与明显粗糙的问题后再行提交。

### 版式方案沟通

**布局框架的讨论也先采用文字形式。** 提交对比页面时附上推荐理由，请用户选择一个方向并说明喜欢与不满意的方面，同时告知：选定后可直接制作完整页面，希望比较多种版式也可以提出。用户要比较版式时，先用文字说明几种布局框架的差异；若用户能够从文字描述中作出决策，就按所选继续推进；若用户希望看到实际视觉效果再制作成首屏，并与选定的方案一同放入对比页面进行最终选择。版式方案之间应保持选定方向的字体体系、色彩方案与控件语法的一致性，仅在布局框架、主视觉摆放方式与页面结构上拉开差异。用户仅回复选择结果后，应将反馈意见整合进去，直接制作完整页面；若用户希望将两个方向合并呈现，应先制作合并后的首屏供用户确认。

### 不适用情形

仅在以下情况中不执行上述流程：若仅需撰写设计说明而不制作页面，则以书面形式记录方向决策。若用户已提供参考图片或品牌规范，或已清晰说明风格要求，则设计方向已然确定：此时候选方案均应限定在该风格范围内，仅在布局框架、主视觉与页面结构上有所差异。若用户明确表示"由你决定""直接开始制作"，或在无人值守环境下执行任务时，不进行询问：候选首屏仍应制作并存入对比页面以备存档，将截图缩小至 480 像素宽度并列查看一次，自主选定并写明理由，随后继续制作完整页面。若任务明确要求仅需要一个方案，则既不询问也不制作对比页面，直接记录方向决策，再按 [设计方向指南](references/design-direction.md) 中的"差异化检验"要求，将其与已拆解的标杆案例进行并列比对，确认不存在视觉雷同问题。

最后留存一份简短的设计说明文档，内容包括：用户核心任务、主动作要求、选定的方向方案、关键状态说明、设备约束条件与验收重点。若已有设计说明文档则直接进行更新。

## 阶段二：视觉与交互结构建立

在设计方向确定、开始制作完整页面时，应首先根据页面类型阅读一组参考资料，其余内容按需获取，不必预先全部载入：说服型页面应阅读视觉语言、素材规范、动效设计与滚动叙事指南；产品界面应阅读视觉语言、素材与动效相关内容。表格中其余条目，仅在页面中出现左列所示内容时再进行阅读：

| 待解决问题 | 参考资料 |
| --- | --- |
| 视觉层级关系、字体选型、色彩体系、空间布局、图标风格、整体风格统一性或减法精修 | [视觉语言](references/visual-language.md) |
| 图像来源判断、图像承担的信息功能：素材选择、配图生成与提示词撰写、图像与页面的一体化整合、实时 3D 与视频处理 | [素材指南](references/media.md) |
| 基本动效与呼应关系、动效手感设定、界面过渡效果、首屏动画、时长控制与检查方法 | [动效规范](references/motion.md) |
| 小游戏、抽奖功能、计时养成机制、强手感操控需求 | [游玩设计](references/play.md)（含素材获取与渲染流程，按其中链接读取素材） |
| 落地页、品牌页、发布页、展览页的滚动动效：区块出场效果、滑动驱动的叙事手法（首屏景深、一镜到底等）与动效库应用 | [滚动叙事](references/scroll-narrative.md) |

在展示功能特性或业务成果时，应首先判断内容是否适合采用卡片形式呈现：依靠大尺寸图片与连续排版建立氛围的页面，不应强行嵌入卡片结构。

新产品应搭建主要内容层级与关键操作流程，不仅仅制作一个美观的默认状态。新建界面或调整操作流程时，应按照 [动效规范](references/motion.md) 做出基本动效；落地页、品牌页、发布页与展览页还必须阅读 [滚动叙事指南](references/scroll-narrative.md)，运用成熟的动效库实现区块按内容出场与滑动驱动的叙事段落，具体手法应根据页面特性进行选择。调整流程与新增功能时应将动效设计写入设计说明；小幅修改则无需添加动效。

交互规则、表单设计规范、状态管理、弹窗机制与响应式实现的规则不在本 Skill 覆盖范围内。若项目或宿主环境已有相应规范，则应遵照执行。若任务明显需要这些体验设计内容，或需要实现流光效果、点阵图案等 SVG 与着色器特效，或在存量项目中优化用户界面、调整流程、新增功能，或将单个组件打磨到极致、使用卡片原型、空间折展结构或卡片内微型抽屉时，按项目与宿主的既有规范自行处理。

构图阶段应首先依据 [素材指南](references/media.md) 判断图像是否能够承担核心信息传递功能或情绪重心。若需要关键素材，应首先选定或制作该素材，再围绕其安排文字内容与操作按钮，不应等待布局填充完毕后再补充图像。

对于既有项目，应优先复用已有的有效设计变量、组件与交互习惯，问题修复应从源头着手，不为单次调整另行创建设计系统，也不将无关的代码重构工作混入视觉设计任务。

## 阶段三：制作并取得实际证据

- 首先完成最具代表性的一页或关键操作流程的检查，确认无误后再向其他页面扩展推广。
- 示例内容应按照真实产品的标准进行编写。模拟数据、生成图片、尚未接入的实际功能应写在交付说明中，不得写入界面：画面上不应出现"示例"、"示意图"、"按钮功能尚未接入"等制作说明性文字，也不应因为原型未接后端就在画面上标注"仅保存在本机"；产品本身即为本地保存、需要向用户特别说明的情况除外。不得伪造业务成功数据、客户评价或产品指标。
- 在目标视口环境下运行并查看效果。日常查看效果时仅截取当前可见区域，积累一批修改后再进行截图；提交评审前与交付前，才使用 [工具](references/tools.md) 中记载的截图工具采集完整证据，一次 `oil_ui_shoot`（`evidence: true`）调用即可输出状态图、200% 缩放局部视图与录屏文件，落地页还需额外录制从顶部滚动至底部的完整视频。录屏应按正常播放速度自行观看一遍：该动的地方没有动效即予以补充，无需逐帧核对。
- 截图工具每次执行都会列出"可读性提示"，在取证环节统一查看：这几项影响实际阅读，应予修正；误报在交付说明里写一句即可。工具不评判风格优劣，也不设审美禁用清单。
- 在实际阅读尺寸下检查中文多行标题、正文内容以及窄屏幕环境下的换行表现。出现文字重叠、被裁切或依靠大量小字才能容纳内容的情况时，应回到内容与布局层面进行修改，不应依靠缩放手段掩盖问题。长页面需要检查整体节奏感，不能仅查看首屏部分。截图保存成功不等于已经进行过视觉检查。

## 阶段四：独立评审与修正

根据改动类型选择评审方式，交接规则参见 [视觉评审派发协议](references/visual-review.md)，评审者按照 [评审手册](references/reviewer-manual.md) 执行：

| 改动类型 | 评审策略 |
| --- | --- |
| 方向探索阶段的对比页面 | 优先提交给用户；候选首屏与版式变体不委派评审，仅用户要求时再进行评审 |
| 新界面设计、整体改版，选定方向之后 | 初版稳定时进行评审，采用 10 分制评分，报告评分结果与剩余差距 |
| 已有界面的单页以上润色，或仅要求评审现有界面 | 按照"存量已有界面润色评审"流程执行，一轮评审，不进行打分 |
| 小幅修改、局部低风险修改 | 由主 Agent 自行检查，不委派评审人员 |

- 若存在隔离环境、能够识别图像的独立执行者，则委派一名没有历史上下文信息的评审人员；若不存在则由主 Agent 自行检查，并标明未进行独立评审的事实。评审者仅查看当前画面、任务要求与约束条件，不查看制作过程与代码内容。
- 当设计风格开始出现漂移倾向、意见反复不一致时，应保留最合适的版本并说明取舍理由；未完成的功能必需部分如实列出。
- 若用户提出文案需要优化，或评审、自查发现文案内容空泛、读起来不自然：若宿主环境中已安装 [oil-tone](https://github.com/oil-oil/oil-tone) 工具则使用该工具修改标题、说明等成段文字；若未安装则先按照本 Skill 的规则修改完善，再建议用户安装该工具继续打磨。按钮、标签与错误提示仍按本 Skill 的规则编写。同一次对话中仅提示一次。
- 并行制作时应按独立页面、素材或方向进行分工，避免多个执行者同时修改同一份共享样式文件。

## 阶段五：验证与交付

检查深度应与改动范围相匹配：小幅修改仅检查改动位置及其相邻元素；精细修改与基线建设需要进行前后对比；新页面、改版与局部重构应执行以下全部检查项。

- 交互流程从真实入口开始直至可观察的结果；保存操作后应重新读取数据，失败后检查输入内容与当前位置是否得到保留。具备保存功能的界面（收藏列表、草稿箱、购物车、计时功能、游戏进度等），验证脚本应至少覆盖刷新后读回与保存失败两种场景；存在次数限制或余额限制时，还应测试用完限制条件的情况。
- 若项目或任务目录中存在检查交互或功能的验证脚本，交付前应由主 Agent 自行执行并通过，涉及异步操作、随机因素或曾偶发失败的应连续执行 3 次，交付说明中记录执行结果；生成页面、截图与取证用途的脚本不在此列。动画与异步状态的检查应等待可观察的状态变化，不依赖固定延时；评审引用的报告不能替代这一步骤。
- 仅执行项目的类型检查与 lint 检查，不执行生产环境的完整构建与全量测试，用户另有要求时除外。若构建失败、接口报错、依赖链接异常等与画面无关的环境问题，则在交付说明中记录一行后予以绕过，不进行问题排查，不修改项目配置。
- 单独执行一次减法优化：每屏应有清晰的主次关系，避免多个元素平分注意力；逐区块删除重复与多余的解释性文字，仅保留删除后会影响理解的句子。减法操作仅删除装饰性内容与重复说明，对象名称、判断依据、当前状态与主动作要素必须保留。在 100% 与 200% 缩放比例下查看关键区域。
- 交付时写一份交付说明，讲清本次做了什么、没做什么及其原因、结论依据的证据在任务目录的哪里。条目、顺序与篇幅按任务本身决定，不套用固定模板；没有发生的内容不必为其补写一行。

设计说明文档、素材文件、截图记录与评审报告应存放于任务目录，不得写入 Skill 安装目录。

## 能力边界声明

无法识别图像时应明确标注"未验证实际视觉"，不得进行视觉打分；不存在可运行环境时，不得宣称交互已通过验证。若用户要求提供可运行的界面而只能提供方案时，应标注未完成的部分。无法生成图片时，可使用手头合适的素材，或交付一份素材需求文档加一个可用的占位版本。仅使用任务已经授权的服务，不自行接入付费服务；无法访问网络时使用已有的参考素材，并说明来源。
